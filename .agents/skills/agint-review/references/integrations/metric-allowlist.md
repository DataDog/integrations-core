# Standard metric allowlist

Applies on integrations-core only. On other repositories, skip this file.

Metrics Platform bills a metric as standard only when its name starts with a `prefix` in dd-analytics' standard metric allowlist (`luigiscripts/billing/usage/standard_metric_allowlist.json` in ddoghq/dd-analytics). Any other metric is billed to the customer as a custom metric. On integrations-core, setup downloads the file to the review folder and lists it in your instruction paths as "Standard metric allowlist", with its source and blob SHA. It's a JSON list: each entry has a `prefix` and usually `origins` (`product`, `subproduct`, `product_detail`).

- Every metric the PR adds is covered by a `prefix` in the allowlist: the `metric_name` of each `metadata.csv` row the PR adds or changes, and each metric name sent by check code the PR adds (`METRICS_MAP` values with the check's namespace, `self.gauge(...)`-style calls). Coverage is a plain string prefix match (`kai.` covers `kai.queue.length`); not every prefix ends in a dot. A new integration, or metrics under a new namespace, with no covering prefix means customers are billed for them as custom metrics (**Request**, PR scope). In the comment, list the metrics no prefix covers (once, on the first uncovered `metadata.csv` row, listing the others), and say the fix is an allowlist entry in ddoghq/dd-analytics, made through the add-metrics-origin process, which usually goes with a metric origin entry in dd-source.
- When a prefix covers the metrics, don't raise anything. Use the matching entry's `origins` only to explain a match you mention (for example `agent` / `integration` / `kai_scheduler` for `kai.`), never as a rule of its own.
- When the instruction paths have no "Standard metric allowlist" entry, setup couldn't download it. Don't guess coverage: raise one **Question** on the first new `metadata.csv` row, saying the allowlist couldn't be checked and asking whether the metrics' prefix is in it.
